# `dissertations.id` — full reference inventory

Compiled for the merge-execution work (`scripts/merge_duplicates.py`). Every
merge repoints or retires exactly two `dissertations` rows; before writing that
script, every table and column in the codebase that can point at
`dissertations.id` had to be found and classified. **Static discovery only** —
this machine cannot reach any database. The list below is built from a full
sweep of `CREATE TABLE` / `REFERENCES` / `dissertation_id` / `diss_id` across
the repository (excluding the stale nested `oak-dissertatsiya/` checkout and
`venv/`/`.venv/`), cross-checked column by column. `scripts/merge_duplicates.py`
also runs a **live `information_schema` check** before every merge and refuses
to proceed if it finds an inbound foreign key that is not in the table below —
so a table added after this document was written cannot be silently missed.

## The trap this inventory exists to avoid

`dissertation_id` is **not always a reference to `dissertations(id)`**. The
Konstruktor writing tool (`blueprints/dissertation.py`) has its own entity,
`diss_projects`, with its own `dissertation_blocks`, `diss_collaborators`,
`diss_notifications`, `messages`/`conversations`, `ai_review_requests`, etc. —
and several of *those* tables also have a column literally named
`dissertation_id`, which is a foreign key to `diss_projects(id)`, **not** to
the OAK-imported `dissertations` table this merge script touches. Confusing the
two would repoint the wrong data. Every row below states which table the column
actually targets.

## 1. Hard foreign keys to `dissertations(id)` — MUST be repointed

| Table.column | Constraint | On delete | Unique? | Handling |
|---|---|---|---|---|
| `user_bookmarks.dissertation_id` | `REFERENCES dissertations(id)` (data.py, blueprints/saved.py, migrations/add_bookmark_notes.sql all lazily create the *same* table — verified byte-identical) | CASCADE | `UNIQUE(user_id, dissertation_id)` | Repoint loser→winner. A user may have bookmarked **both** records; the composite unique constraint would then reject a plain `UPDATE`. The merge deletes the now-redundant loser-side bookmark row first (`DELETE ... WHERE dissertation_id = loser AND EXISTS (... user already has winner)`), then updates the rest. |
| `specialty_notifications_log.dissertation_id` | `REFERENCES dissertations(id)` (blueprints/subscriptions.py) | none (`NO ACTION`) | no | Plain `UPDATE`. No uniqueness, so no conflict is possible. This is a delivery-history log for the "ixtisoslik obunasi" feature; kept accurate so the log continues to read correctly after a merge. |

Both are safe under `ON DELETE CASCADE`/`NO ACTION` regardless, because the
merge **never deletes** the losing `dissertations` row — but the repoint still
matters so a user's bookmark, or a subscription log entry, follows the record
that is now the canonical one.

## 2. Soft references (no DB-level FK, but logically point at `dissertations.id`)

| Table.column | Where | Unique? | Handling |
|---|---|---|---|
| `duplicate_candidates.record_id_1` / `record_id_2` | migration 004, `record_type='dissertation'` | `UNIQUE(record_type, record_id_1, record_id_2)` | The candidate row being executed becomes `status='merged'`. Any **other** candidate row that pairs the loser with a third record is repointed to the winner (with canonical `id1 < id2` reordering); if that would collide with an already-existing `(winner, third)` row, the now-redundant loser-side row is dropped rather than the UPDATE erroring out — the pairing information is not lost, it already exists on the surviving row. |
| `data_quality_issues.record_id` | migration 004, `record_type='dissertation'` | no | **Deliberately NOT repointed.** Migration 004's own docstring frames `record_id` as polymorphic-by-design with "integrity checked in application code", and issue rows are ephemeral scan output — CASCADE-deleted with their run, regenerated by the next scan. Repointing historical issue rows would misrepresent *when* an issue was found against *which* id at scan time. |
| `data_quality_fix_log.record_id` | this branch's migration 006 | no | Forward-only: the merge script is the only writer, and it always writes the **current** (winner) id. No repoint needed. |
| `diss_notifications.payload->>'diss_id'` | `blueprints/dissertation.py` (Konstruktor notifications table) — the *column* `diss_notifications.dissertation_id` is a real FK to **`diss_projects(id)`**, unrelated; the OAK dissertation id is stashed inside the JSONB `payload` by `blueprints/olimlar_catalog.py::notify_scholar_follows` (see its own comment: *"dissertations EMAS... himoya id'sini payload ichida saqlaymiz"*) | no | **Deliberately NOT repointed.** It is a snapshot of an already-sent notification's display text (scholar name, student name, title excerpt) plus the id only for de-duplication of *future* sends. Rewriting history here has no user-visible benefit and risks corrupting the de-dup check for events already fully processed. |

## 4. `dissertations` columns that need care during a merge, but are not FKs

| Column | Note |
|---|---|
| `oak_id` | `UNIQUE` (`migrate_columns.py`: `ALTER TABLE dissertations ADD CONSTRAINT dissertations_oak_id_key UNIQUE (oak_id)`; `upload.py` independently declares `oak_id TEXT UNIQUE` when lazily adding the column — harmless duplication since `ADD COLUMN IF NOT EXISTS` is a no-op once the column exists either way). **Never copied by the fill step**: copying the loser's `oak_id` onto the winner while the loser still holds the same value would violate the unique constraint, and clearing it from the loser would destroy that record's own link back to its OAK announcement — which the merge is not supposed to do, since the loser is retained, not deleted. `oak_id` still counts toward the *completeness score* used to pick the winner (see `data_quality/merge_review.py`), it is just excluded from copying. |
| `data_quality` | The pre-existing coarse flag (`complete`/`missing_author`/`incomplete`) from `scripts/flag_data_quality.py`. Not touched by the merge — it is recomputed by the next scan/flag pass, same as for any other edited row. |
| `merged_into_id` / `merged_at` | **New**, added by migration 006 in this branch. `merged_into_id` is nullable, self-referencing (`REFERENCES dissertations(id) ON DELETE SET NULL`); when set, this row was merged away and is not the canonical record. `merge_duplicates.py` refuses to merge a record that already has `merged_into_id` set on either side of the pair — this also rules out merge chains/cycles by construction. |

## 5. Runtime safety net

`data_quality.repository.discover_fk_references_to_dissertations(conn)` queries
`information_schema.table_constraints` / `key_column_usage` /
`constraint_column_usage` for every foreign key whose target is
`dissertations.id`, and `assert_no_unknown_fk_references(conn)` compares the
result against the hard-FK table in §1 above
(`data_quality.repository.KNOWN_FK_REFERENCES_TO_DISSERTATIONS`).
`scripts/merge_duplicates.py` calls this once before touching anything; an
unrecognized foreign key aborts the whole run before a single row is written.
This is the safety net for "a table gets added after this document is
written" — the static inventory is what a human reads, the live check is what
protects the data in that case.
